## 动机：为什么先讲循环

这一章是全书的基石。我们从一个看似简单的问题出发：

> 大模型只会生成文字，怎么让它「自己动手」完成一件任务？

答案是一层薄薄的框架——**核心循环**。它是所有 agent（你本地的 opencode、Codex，到云端服务百万用户的 xiaoaiclaw）共同的心跳。后面七章讲的工具调用、上下文、沙箱、多 agent，**全是在这个循环之上加装的能力**。

理解这一章，你就抓住了 agent harness 的骨架。

## 直觉层：像一场「边想边动手」的对话

想象你和朋友合作修车：

1. 你说「帮我把发动机修好」（**发起请求**）
2. 朋友想：「得先拆下气缸盖」（**模型决定下一步**）
3. 朋友真的去拿扳手拆螺丝（**执行工具**）
4. 拆开发现活塞坏了，说「得换活塞」（**结果回填，重新思考**）
5. 循环 3→4，直到朋友说「修好了」（**不再动手，给出答案**）

关键在第 4 步：如果朋友拆开之后不「看到」结果，他就永远停在「我要拆气缸盖」这一句。

## 根源理解：为什么 agent 一定是「循环 + 消息数组」

这是本书最重要的一个推导，请慢读。

**LLM 是一个无状态函数**：

```
f(messages) → message
```

输入一串消息，输出一条消息。它**不记得上一次调用**——你问「123×456 等于多少」，它不知道上一轮它刚算过 56088。

**但 agent 需要有状态**：它得记住「我算完了，结果是 56088」，才能接着往下走。

让无状态的 LLM 变成有状态的 agent，办法**只有一个**：把历史消息**全部喂回去**。

于是两个结论自动浮出水面：

1. **消息数组 = agent 的全部状态**。除此之外没有任何「记忆」——没有隐藏变量、没有数据库（那是后面章节的优化）。
2. **循环 = 反复调用 f，每次把新消息追加到数组末尾，再喂回去**，直到模型不再要求调工具。

这就是为什么 pi / opencode / Claude Code 的核心，都是一个 `while` 循环 + 一个消息数组，**无一例外**。这不是巧合，是无状态函数的必然推论。

## 从零实现：一个能跑起来的循环

理解了根源，现在把它写成代码。下面是我们从零构建的 `d2a-harness` 的核心（完整代码见 `d2a-harness/src/step-01-loop/`，零依赖，Node 原生直接跑）：

```ts
// 消息数组 = agent 的唯一状态。四种角色构成一次对话的最小单位。
type Message = {
  role: "system" | "user" | "assistant" | "tool";
  content: string;
  tool_calls?: ToolCall[];   // assistant 的「意图」：我想调哪个工具
  tool_call_id?: string;      // tool 消息用它关联回那次调用
};

async function runLoop(userRequest, tools, options) {
  const maxTurns = options.maxTurns ?? 10;   // 轮数上限，防止死循环
  const messages = [
    { role: "system", content: "你是助手，需要计算时调用 calculator。" },
    { role: "user", content: userRequest },
  ];

  for (let turn = 0; turn < maxTurns; turn++) {
    // ① 调用模型：把「状态」整体喂给无状态函数 f
    const reply = await callLLM(messages, tools);
    messages.push(reply);

    // ② 判断：模型要调工具吗？
    const toolCalls = reply.tool_calls ?? [];
    if (toolCalls.length === 0) return messages;   // 没有 → 任务完成

    // ③ 执行 + 回填：把结果追加进状态，下一轮模型就能「看到」
    for (const tc of toolCalls) {
      const tool = tools.find((t) => t.name === tc.function.name);
      const result = tool
        ? String(await tool.execute(JSON.parse(tc.function.arguments)))
        : `错误：未知工具 ${tc.function.name}`;
      messages.push({ role: "tool", content: result, tool_call_id: tc.id });
    }
  }
  return messages;   // 达到上限仍未结束（真实 harness 在此触发熔断）
}
```

这段代码真实可运行。跑 `npm run step-01`，你会看到循环的完整轨迹：

```text
[user] 帮我算一下 123 * 456 等于多少
[assistant] 想调工具: calculator({"expression": "123 * 456"})
[tool]  → 56088
[assistant] 123 × 456 = 56088
```

模型**先要求调工具，再看到结果，最后给出答案**——这就是「有状态」的来源。注意四步里最容易被忽略的是第 ③ 步：不把结果 `push` 回去，模型就永远卡在「我要调 calculator」这一句。

## 对照基准：pi 的 agent-loop.ts 怎么实现

现在把我们的 20 行，放进真实 harness 里看。pi 的核心循环在 `packages/agent/src/agent-loop.ts`。先看它的**设计框架**——一个函数怎么拆成一组协作的函数：

```text
runLoop（主循环，:157）
├─ 双层循环
│   ├─ 外层 while(true)（:179）              ← 应对用户中途插话（follow-up）
│   └─ 内层 while(hasMoreToolCalls)（:183）  ← 核心循环，处理工具调用
├─ streamAssistantResponse（:381）           ← 调用模型，流式输出
├─ executeToolCalls（:508）                  ← 执行工具
│   ├─ prepareToolCall（:708）               ← 找工具 + 校验参数 + beforeToolCall 权限
│   ├─ executePreparedToolCall（:821）       ← 真正调用 tool.execute
│   └─ createToolResultMessage（:930）       ← 封装结果消息
└─ finishTurn（配置钩子，:286）              ← 判断是否继续/结束
```

对比我们写的：**我们只有 `runLoop` 一个函数，pi 把它拆成了 7 个**。为什么拆？因为真实 harness 要解决我们没面对的问题：流式输出、参数校验、权限、并行执行、事件通知。每一块对应本书后面的一章。

### 真实代码（annotated）

下面贴出 pi 的 `runLoop` 关键段，逐行标注（`// ←` 是我们的对应物）：

```ts
// packages/agent/src/agent-loop.ts:157（已精简，保留骨架）
async function runLoop(...) {
  // 外层循环：用户可能中途插话，来了新消息就继续
  while (true) {                                    // :179  ← 我们的 for 循环
    let hasMoreToolCalls = true;
    // 内层循环：处理工具调用，这是真正的「核心循环」
    while (hasMoreToolCalls || pendingMessages.length > 0) {  // :183
      // ...准备请求、处理 steering 消息...

      const message = await streamAssistantResponse(...);  // :242 ← 我们的 callLLM

      // 检查工具调用：工具调用是 content 的一种类型，可和文本混排
      const toolCalls = message.content.filter(c => c.type === "toolCall");  // :259
      //                                                 ↑ ← 我们的 reply.tool_calls ?? []

      hasMoreToolCalls = false;
      if (toolCalls.length > 0) {
        const executed = await executeToolCalls(...);   // :270 ← 我们的 tool.execute
        toolResults.push(...executed.messages);
        hasMoreToolCalls = !executed.terminate;         // :272 ← 我们的「还有工具吗」
        for (const result of toolResults) {
          currentContext.messages.push(result);         // :275 ← 我们的 messages.push
        }
      }

      // 判断是否结束：交给 finishTurn 钩子，而非硬编码
      const decision = await config.finishTurn?.(...);  // :286 ← 我们的 maxTurns
      if (decision?.action === "end") { return; }       // :289
    }
    // 检查 follow-up 消息，有则继续外层循环
  }
}
```

### 逐块对比：具体差在哪

先看全局：我们 1 个函数，pi 拆成了 7 个协作函数，虚线标出每一块的对应关系：

<DiagramFrame src="/diagram/loop/comparison.html" title="我们 vs pi：骨架不变，逐环长大（可交互）" />

再看逐块的细节：

| 环节 | 我们写的 | pi 的实现 | **具体区别** |
|------|---------|-----------|-------------|
| 循环结构 | 一个 `for` | 双层 `while`（`:179`/`:183`） | 内层是核心循环；外层额外处理「用户中途插话」——真实对话里用户会打断 agent |
| 调用模型 | `callLLM` 一次性返回 | `streamAssistantResponse`（`:242`） | 流式：边生成边发事件，UI 能实时渲染「正在想…」，不用等整段完成 |
| 工具调用 | 顶层 `tool_calls` 字段 | `content` 数组里 `type==="toolCall"`（`:259`） | 工具调用能**和文本混排**在同一条消息里（先解释一句再调工具） |
| 执行工具 | 直接 `tool.execute` | `executeToolCalls`（`:270`）五步 | 拆成：找工具 → 校验参数 → 权限检查（`beforeToolCall`）→ 执行 → 后处理 |
| 回填结果 | `messages.push(result)` | `currentContext.messages.push(result)`（`:275`） | **完全一样**——这是所有 harness 的不变量 |
| 结束条件 | `maxTurns` 硬上限 | `finishTurn` 钩子（`:286`） | 结束交给可配置的钩子，能显式决定 `end` / `continue`，更灵活 |

### 一句话结论

我们写的 20 行，就是 pi 那 400 行的**骨架**。pi 多出来的 380 行，不是「更聪明」，而是**把每一环拆开、加装生产必需的能力**——流式、校验、权限、并行、事件。这 380 行，就是本书后面七章要逐一拆开的内容。

## 小结

- LLM 是**无状态函数**，agent 的「状态」只能是**消息数组**，循环是「反复调用 + 回填」。
- 核心循环四步：**调用模型 → 判断 → 执行工具 + 回填 → 循环/结束**。
- 「回填结果」是灵魂：不喂回结果，agent 就卡死在同一步。
- 真实 harness（pi 的 `agent-loop.ts`）与我们写的 20 行**结构同构**，多出来的是流式、批处理、事件等子系统。
- `maxTurns` 之类的保护，是生产级与玩具的分水岭。
