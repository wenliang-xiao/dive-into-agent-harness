## 动机：把「执行工具」这一环拆开

上一章的核心循环里，我们只写了一句 `tool.execute(...)`，就把「执行工具」一笔带过了。但这一环其实是 agent 最复杂的地方之一：

- 模型**怎么知道**有哪些工具、各要什么参数？
- 模型给的参数**能信吗**？
- 工具执行**出错**了怎么办？

这一章把「执行工具」彻底拆开。它是你日常用 Claude Code / opencode 时，那些「读文件、改文件、跑命令」背后真正发生的事。

## 直觉层：给模型一张「能力菜单」

模型本来只会「说」，工具让它能「做」。但要让模型知道「能做什么、怎么做」，你得先给它一份**说明书**：

- **说明书**（工具声明）：列出每个工具的名字、用途、要什么参数——像菜单上「计算器：要一个字符串表达式」。
- 模型需要时，说「我要用**计算器**，参数是 `123*456`」（**工具调用**：名字 + 参数）。
- 你递上计算器，算完把结果贴回对话（**结果回传**）。

关键在「说明书」：不给说明书，模型根本不知道有计算器，更不知道该怎么用它。

## 根源理解：为什么是「声明 → 校验 → 执行」

从 step-01 的结论出发——LLM 是只会生成文字的无状态函数。要让它「执行动作」，必须补上三层：

1. **声明（能力菜单）**：模型不知道你有哪些工具。所以调用模型时，要把工具声明（名字 + 描述 + 参数 Schema）一起传进去。**为什么是 JSON Schema？** 因为模型需要**结构化地**理解「要什么参数、什么类型、哪些必填」——Schema 既能被模型读懂，又能被代码**校验**，一举两得。

2. **校验（参数不可信）**：模型输出是不可信的。它可能漏传必填参数、给错类型、甚至被 prompt injection 塞进恶意参数。所以**执行前必须校验**——用同一个 Schema 去验模型给的参数，不合格就拒绝执行。

3. **执行 + 封装（错误兜底）**：工具执行出错（参数非法、运行时异常），**不能崩掉循环**。要把错误「封装成一条 tool 结果」回传给模型，模型看到错误后自己纠正。循环照常继续。

于是「执行工具」从一句，长成了四步：

```text
声明(Schema) → 解析参数 → 校验 → 执行 → 封装结果
```

## 从零实现：声明 → 校验 → 执行 → 封装

下面是从零实现的完整链路（`d2a-harness/src/step-02-tools/`）：

```ts
// ① 声明：JSON Schema，模型靠它理解参数，代码靠它校验参数
type Tool = {
  name: string;
  description: string;
  parameters: {
    type: "object";
    properties: Record<string, { type: string }>;
    required?: string[];
  };
  execute: (args: Record<string, unknown>) => Promise<string> | string;
};

// ② 校验：模型给的参数不可信，执行前先验
function validateArguments(tool, rawArgs) {
  for (const key of tool.parameters.required ?? []) {
    if (!(key in rawArgs)) return { ok: false, error: `缺少必填参数 ${key}` };
  }
  for (const [key, spec] of Object.entries(tool.parameters.properties)) {
    const val = rawArgs[key];
    if (val === undefined) continue;
    if (spec.type !== typeof val) {
      return { ok: false, error: `参数 ${key} 应为 ${spec.type}，实际是 ${typeof val}` };
    }
  }
  return { ok: true, args: rawArgs };
}

// ③④ 执行 + 封装：每一步错误都「封装成 tool 结果」，而不是崩掉循环
async function executeToolCall(tools, tc) {
  const tool = tools.find((t) => t.name === tc.function.name);
  if (!tool) return `错误：未知工具 ${tc.function.name}`;      // 未知工具

  let rawArgs;
  try { rawArgs = JSON.parse(tc.function.arguments); }
  catch { return `错误：参数不是合法 JSON`; }                    // 解析失败

  const v = validateArguments(tool, rawArgs);
  if (!v.ok) return `错误：${v.error}`;                          // 校验失败

  try { return String(await tool.execute(v.args)); }
  catch (e) { return `错误：${e.message}`; }                     // 执行异常
}
```

注意这段代码的设计哲学：**所有错误都 `return` 一条错误字符串，从不 `throw`**。因为错误要回传给模型（让它看到、纠正），而不是让循环崩溃。

async function prepareToolCall(...) {
  const tool = tools.find(t => t.name === toolCall.name);   // ← 我们的「找工具」
  if (!tool) return { kind: "immediate", result: error(`Tool not found`) };

  const validatedArgs = validateToolArguments(tool, toolCall);  // ← 我们的「校验」
  if (config.beforeToolCall) { /* 权限检查，下一章展开 */ }

  return { kind: "prepared", tool, args: validatedArgs };
}

// executePreparedToolCall(:821)：真正执行
const result = await prepared.tool.execute(...);             // ← 我们的「执行」

// createToolResultMessage(:930)：封装成消息

## 小结

- 工具调用 = **声明（JSON Schema）→ 校验 → 执行 → 封装结果**。
- **声明是 Schema**：既能被模型读懂，又能被代码校验，一举两得。
- **参数不可信**：模型可能漏参数、给错类型、被注入，执行前必须校验。
- **错误要封装不崩溃**：所有错误 `return` 成 tool 结果回传，模型看到后自行纠正，循环继续。
- pi 把这一步拆成 5 个函数，多的是**顺序/并行策略**和**权限检查**。
