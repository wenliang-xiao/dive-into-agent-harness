## 动机：窗口有限，内容无限

前两章我们把消息都塞进上下文，模型就能一直「看到」历史。但有个硬约束：**上下文窗口是有限的**（几十万 token 封顶），而 agent 要处理的内容——代码、文件、工具结果、多轮历史——**无限增长**。

窗口塞满会怎样？Anthropic 给了一个词：**Context Rot（上下文腐烂）**：

> 上下文里的 token 越多，模型准确回忆其中信息的能力就越下降。

所以上下文管理不是「把东西都塞进去」，而是持续回答：**往窗口里写什么、写多少、满了之后丢掉什么**。这直接决定一个 agent 能跑多长、多准、多便宜。

## 直觉层：上下文是模型的「草稿纸」

把上下文窗口想象成模型手边一张**固定大小的草稿纸**：

- 模型边干活边写：你的要求、读过的文件、工具结果、之前的想法。
- 草稿纸**大小固定**，写得越满，模型越难从满纸字里找到关键信息（这就是 Context Rot）。
- 快写满时你得做选择：**擦掉不重要的**、**把一大段浓缩成一行摘要**、或**把细节抄到别处，只留个「去哪里找」的索引**。

Anthropic 把这套手艺总结成四个动作：**Write（写入）→ Select（挑选）→ Compress（压缩）→ Isolate（隔离）**。

## 根源理解：为什么「压缩」用摘要替换

从 step-01 的结论推：**消息数组 = agent 的全部状态**。这条数组有上限，所以必须「丢东西」。但怎么丢？

最朴素的答案：**压缩**——把最早的一大段历史，替换成一段摘要。

```text
[system, user, assistant, tool, assistant, tool, ...100条...]  ← 太长，塞不下
        ↓ 压缩
[system("摘要：之前讨论要算 123*456..."), ...最近4条]           ← 短了，保住关键信息
```

核心洞察：**摘要保留「信息」、丢弃「细节」——用信息密度换空间**。这就是「压缩」和「删除」的本质区别：删除丢信息，压缩保关键。

压缩有两个核心参数：

- **window**：窗口上限（模型能装多少 token）
- **buffer**：预留余量（不贴着上限跑，给模型输出留空间）

逼近 `window - buffer` 才触发压缩——这就是「何时压」。

## 从零实现：token 预算 + 摘要压缩

`d2a-harness/src/step-03-context/` 的最简实现：

```ts
// ① 估算 token（教学简化：中文 1 字 1 token，其余 4 字符 1 token）
function estimateTokens(messages) {
  return messages.reduce((sum, m) => {
    const cjk = (m.content.match(/[\u4e00-\u9fff]/g) ?? []).length;
    return sum + cjk + Math.ceil((m.content.length - cjk) / 4);
  }, 0);
}

// ② 压缩触发：逼近 window - buffer 才压
function needsCompact(messages, window, buffer) {
  return estimateTokens(messages) > window - buffer;
}

// ③ 压缩：摘要替换最早的历史（保留最近 keepRecent 条）
async function compact(messages, summarize, keepRecent = 4) {
  const history = messages.slice(0, -keepRecent);
  const summary = await summarize(history);
  return [
    { role: "system", content: "之前对话的摘要：" + summary },
    ...messages.slice(-keepRecent),
  ];
}
```

两个要点：**留 buffer**（不贴着上限跑）、**摘要替换而非删除**（保住关键信息）。真实实现远比这精细——下面看 Claude Code 的五级状态机。

## 对照基准：Claude Code 的五级压缩与四层记忆

> 说明：Claude Code 闭源，以下来自 source map 还原的源码分析，标注「基于 source map 还原，非官方源码」。

先看全局——cc 不是「满了就一次性压」，而是**多档预警状态机**，从最轻的动作开始逐级加码：

关键源码常量（`autoCompact.ts`）：

```ts
const MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000;  // 摘要最长 2 万 token
const AUTOCOMPACT_BUFFER_TOKENS = 13_000;      // 逼近上限的预留余量 ← 我们的 buffer
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3; // 熔断器
```

最震撼的是熔断器背后的一段生产事故注释（`autoCompact.ts:68-70`）：

```ts
// BQ 2026-03-10: 1,279 sessions had 50+ consecutive failures (up to 3,272)
// in a single session, wasting ~250K API calls/day globally.
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
```

1279 个会话里，压缩失败后不停重试，一天浪费 25 万次 API 调用。**三行代码止血**：连续失败 3 次就停。这是上下文工程在生产里的真实挑战——不是算法多高级，而是「失败时别死循环」。

### 记忆：只存「推导不出来的东西」

压缩解决「窗口内塞不下」，记忆解决「跨会话持久化」。cc 的记忆系统本质是**基于文件的分层指令系统**，不是向量数据库。四类记忆（`memdir/memoryTypes.ts`）：

| 类型 | 含义 | 示例 |
|------|------|------|
| **user** | 用户画像 | 「用户是数据科学家，首次接触 React」 |
| **feedback** | 行为指导 | 「用户不要 trailing summary」 |
| **project** | 项目动态 | 「3 月 5 日后冻结合并」 |
| **reference** | 外部指针 | 「pipeline bugs 在 Linear INGEST 项目」 |

一句话点破本质：**「CLAUDE.md is a collaboration contract, not a knowledge base」**——明确**不保存**能从项目状态推导出的东西（代码模式 grep 可得、git 历史 git log 可得）。记忆只存「推导不出来」的隐性知识。

一句话总结：我们写的「token 预算 + 摘要压缩」，就是 cc 五级压缩的**骨架**。cc 多出来的，是把压缩拆成**逐级升级的 5 档**、加**熔断器**防死循环、并用**四层记忆**解决跨会话持久化。

## 小结

- 窗口有限，塞太满会 **Context Rot**；管理动作是 Write / Select / Compress / Isolate。
- 压缩的本质：**摘要替换原文**——保信息、丢细节，用密度换空间。
- 两个核心参数：**window**（上限）+ **buffer**（余量），逼近 `window - buffer` 才压。
- cc 用**五级压缩状态机**从轻到重（Snip → Microcompact → Collapse → Auto Compact），每级有熔断器防死循环。
- 记忆是**文件指令系统**，只存「推导不出来」的 user / feedback / project / reference 四类。
