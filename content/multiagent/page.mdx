## 动机：单 agent 有极限

前面五章，我们都在讲「一个 agent 干所有事」。但单 agent 有两个硬伤：

- **上下文爆炸**：复杂任务要读几十个文件、跑几十次工具，中间过程全堆在同一个窗口里，很快 Context Rot（第 4 章）。
- **任务混杂**：既要调研、又要实现、还要验收，一个「大脑」来回切换，效率低、易分心。

解法是把大任务**拆给多个 agent 并行干**。它的核心价值就一句话：**把子任务的探索与中间过程隔离在独立上下文里，主 agent 只拿结论。**

## 直觉层：包工头 + 工人

想象一个包工头（协调者）带着一群工人（worker）：

- 包工头接到「装修一套房」，**拆任务**：A 刷墙、B 铺地板、C 走水电。
- 包工头**派活**给工人，工人各自在自己的工位干活，互不干扰。
- 包工头**验收**：活干得不行打回去重做，干错了叫停。
- 包工头自己**不搬砖**——只做拆解、派发、验收、纠偏。

工人的工位彼此独立（隔离的上下文），包工头不知道每个工人的每一步，只知道「墙刷好了没有」。

## 根源理解：Isolate 的落地

回顾第 4 章的 Write / Select / Compress / **Isolate** 四策略。多 agent 就是 **Isolate（隔离）** 的落地：

1. 单 agent 的上下文会爆（step-03 的 Context Rot）。
2. 把子任务放进**独立的上下文**（独立的消息数组 = 独立状态），探索和试错留在子窗口里。
3. 主 agent 只拿结论——`dispatchWorker` 返回的是 worker 的**最终输出**，不是全过程。

这呼应 step-01 的结论：**消息数组 = agent 的状态**。既然每个 agent 的状态是独立的消息数组，那么「隔离上下文」就是「给每个 worker 一份独立的消息数组」。

## 从零实现：协调者 + worker

`d2a-harness/src/step-05-multiagent/`：

```ts
// worker：独立循环 + 独立上下文
async function dispatchWorker(task, tools, config) {
  return runAgent(
    "你是专注执行子任务的 worker，完成后只返回结论。",  // 独立的 system
    task,
    tools,
    config,          // worker 有自己的 messages，中间过程不外泄
  );
}

// 协调者：拆任务 → 派发 → 汇总
async function coordinator(subtasks, tools, config) {
  const run = (task, i) => dispatchWorker(task, tools, config);

  if (config.parallel === false) {
    const results = [];
    for (let i = 0; i < subtasks.length; i++) results.push(await run(subtasks[i], i));
    return results;                       // 串行：一个接一个
  }
  return Promise.all(subtasks.map(run));  // 并行：同时跑
}
```

三个关键点：

1. **worker 有独立 messages**——子任务的探索、试错都在自己的窗口里，不污染主上下文。
2. **主 agent 只拿结论**——`dispatchWorker` 返回 worker 的最终输出，不是全过程。
3. **并行 vs 串行**——互不依赖的子任务用 `Promise.all` 同时跑，有依赖则串行。

## 对照基准：Claude Code 的 Coordinator Mode

> 说明：以下来自 source map 还原分析，标注「基于 source map 还原，非官方源码」。

cc 的多 agent 协调者有个惊人的设计——**编排逻辑不是代码，而是 prompt**。传统系统用代码定义任务 DAG，cc 把这些写进 system prompt 指令：

| prompt 里的「编排指令」 | 传统系统的对应物 |
|----------------------|----------------|
| "Launch independent workers concurrently" | 并行调度策略 |
| "Read-only tasks run in parallel; Write-heavy one at a time" | 并发控制 / 锁 |
| "Do not rubber-stamp weak work" | 质量检查逻辑 |

> "The multi-agent coordinator is interesting because the orchestration algorithm is a prompt, not code." — Alex Kim

协调者与 worker 通过**工具集隔离**实现分工：协调者只有管理类工具（`AgentTool` 派发、`SendMessageTool` 发指令、`TaskStopTool` 叫停），worker 只有执行类工具（Bash/FileEdit/Grep）。协调者**不能**改文件，worker **不能**派发 worker——职责通过工具集硬隔离。

一句话总结：我们写的「协调者 + worker + 独立上下文」，就是 cc Coordinator Mode 的骨架。cc 的特殊之处，是把「编排」本身也交给了 prompt（而非代码），并把分工硬编码进工具集。

## 编排的鲁棒性：durable execution

多 agent 编排有个隐藏的痛点：worker 跑着跑着挂了——进程崩溃、网络超时、任务被取消。如果编排逻辑是「跑完就完」，整个任务得重来，已经完成的 side effect（比如已经改好的文件）还要重做一遍。

**durable execution（持久执行）** 解决的就是这个：

- 把编排建模成**状态机 / 图**：节点是函数（调用 worker、执行工具），边是转换。
- 每个节点完成后 **checkpoint** 一次状态。
- 从任何失败点**恢复**，从最后一个成功 checkpoint 继续，**不重做已确认的 side effect**。

对应到我们的 `coordinator`：现在它是「派发 → 等结果 → 汇总」，挂了就没了。加上 checkpoint 后，每个 worker 完成就记录一次，挂了从最后一个完成的 worker 继续，不用重派已经完成的。素材里的 durable-harness 就是这个思路的专门实现。

一句话：**多 agent 编排从「跑完就完」进化到「随时可恢复」，靠的是把编排从「函数调用」升级成「可 checkpoint 的状态机」。**

## 算法变体：为什么它们需要「架构承载」

第 1 章的核心循环是 **ReAct**（边想边做）。但 agent 的「思考策略」不止这一种，而它们的区别**不在 prompt，在于 harness 要提供什么架构支撑**：

| 算法 | 核心思想 | harness 要提供的架构 |
|------|---------|---------------------|
| ReAct | 边想边做（interleave） | 一个循环 + 消息数组（第 1 章） |
| ReWOO | plan 和 execute 分离 | 规划阶段 + 执行阶段，两个阶段 |
| Reflexion | 失败后写「反思」再试 | 试错循环 + 记忆写入（反思存进记忆） |
| ToT / LATS | 树状搜索 + 回退 | 树状状态管理 + 节点回退 |

关键洞察：**这些算法不是「换个 prompt」就能跑，它们需要 harness 提供不同的架构承载**——ReWOO 要阶段分离、Reflexion 要记忆写入、ToT 要树状回退。这就是「agent = LLM + harness」的完整含义：算法是上层，harness 是承载它的架构。只懂算法不懂 harness，算法跑不起来；只懂 harness 不懂算法，不知道 harness 该承载什么。

## 小结

- 多 agent 解决单 agent 的**上下文爆炸**和**任务混杂**——核心是「隔离子任务上下文，主 agent 只拿结论」。
- 协调者做**拆解、派发、验收、纠偏**，不自己搬砖；worker 有独立的消息数组。
- 协调者与 worker 通过**工具集隔离**：管理类 vs 执行类。
- cc 的「**Prompt 即编排**」：编排算法写在 prompt 里，而非代码 DAG——大胆但有风险。
- 多 agent 是上下文工程 **Isolate** 策略的落地。
- 多 agent 编排要「随时可恢复」：durable execution 用状态机 + checkpoint 把「函数调用」升级成「可恢复的图」。
- 算法变体（ReWOO/Reflexion/ToT）的区别在 harness 架构承载，不是 prompt——算法是上层，harness 是承载。
