## 动机：单 agent 有极限

前面五章，我们都在讲「一个 agent 干所有事」。但单 agent 有两个硬伤：

- **上下文爆炸**：一个复杂任务要读几十个文件、跑几十次工具，中间过程全堆在同一个窗口里，很快 Context Rot。
- **任务太杂**：既要调研、又要实现、还要验收，一个「大脑」来回切换，效率低、易分心。

解法是把大任务**拆给多个 agent 并行干**——这就是多 agent 编排。它的核心价值就一句话：**把子任务的探索与中间过程隔离在独立上下文里，主 agent 只拿结论。**

## 直觉层：包工头 + 工人

想象一个包工头（协调者）带着一群工人（worker）：

- 包工头接到「装修一套房」，**拆任务**：A 刷墙、B 铺地板、C 走水电。
- 包工头**派活**给工人，工人各自在自己的工位干活，互不干扰。
- 包工头**验收**：活干得不行就打回去重做，干错了就叫停。
- 包工头自己不搬砖——他只做**拆解、派发、验收、纠偏**。

工人的工位彼此独立（隔离的上下文），包工头不用知道每个工人的每一步，只知道「墙刷好了没有」。

## 机制层：一个极简的 subagent 派发

用最少的代码表达这个模式——协调者把任务派给一个独立的 agent loop：

```ts
// 协调者的核心：把子任务派发给一个独立 agent，只拿最终结论
async function dispatchWorker(task: string): Promise<string> {
  // 关键：worker 有自己独立的 messages（隔离的上下文）
  const workerMessages: Message[] = [
    { role: "system", content: "你是专注执行子任务的 worker，完成后只返回结论。" },
    { role: "user", content: task },
  ];

  // worker 跑自己的完整 agent loop（就是第二章那个循环）
  const conclusion = await agentLoop(workerMessages);

  return conclusion; // 主 agent 只拿到结论，看不到 worker 的中间过程
}

// 协调者主循环：拆任务 → 派发 → 汇总
async function coordinator(userRequest: string) {
  const subtasks = await decompose(userRequest); // 拆成子任务
  const results = await Promise.all(subtasks.map(dispatchWorker)); // 并行派发
  return summarize(results); // 汇总
}
```

三个关键点：

1. **worker 有独立 messages**——子任务的探索、试错都在自己的窗口里，不污染主上下文。
2. **主 agent 只拿结论**——`dispatchWorker` 返回的是 worker 的最终输出，不是全过程。
3. **并行**——互不依赖的子任务用 `Promise.all` 同时跑。

## 源码层：Claude Code 的 Coordinator Mode

> 说明：以下来自 source map 还原分析（《Claude code 代码泄露》），标注「基于 source map 还原，非官方源码」。

### 「Prompt 即编排」：编排算法是 prompt，不是代码

cc 的多 agent 协调者有个令人意外的设计——**编排逻辑不是代码，而是 prompt**。传统系统用代码定义任务 DAG（依赖图），cc 把这些写进 system prompt 指令：

| prompt 里的「编排指令」 | 传统系统的对应物 |
|----------------------|----------------|
| "Launch independent workers concurrently — don't serialize work" | 并行调度策略 |
| "Read-only tasks run in parallel; Write-heavy tasks one at a time" | 并发控制 / 锁 |
| "You must understand findings before directing follow-up work" | 任务间依赖管理 |
| "Do not rubber-stamp weak work" | 质量检查逻辑 |

> "The multi-agent coordinator is interesting because the orchestration algorithm is a prompt, not code." — Alex Kim

这意味着编排的可靠性**完全依赖模型的 instruction following 能力**，而非确定性代码。大胆，但有风险。

### 协调者与 worker 用不同的工具集

分工通过**工具集隔离**实现：

```text
协调者的工具（管理类）：
├── AgentTool        — 派发新 worker
├── SendMessageTool  — 给已有 worker 发后续指令
└── TaskStopTool     — 停掉走错方向的 worker

Worker 的工具（执行类）：
├── Bash / FileRead / FileEdit / Grep / Glob / MCP 工具（标准工具集）
```

协调者**不能**直接改文件（没有 FileEdit），worker **不能**派发新的 worker（没有 AgentTool）——职责通过工具集硬隔离。

### 上下文隔离是「Isolate」策略的落地

回到上一章的 Write/Select/Compress/Isolate 四策略。多 agent 就是 **Isolate（隔离）** 的落地：把子任务放进独立 loop，上下文完全隔离。cc 官方表格把 SubAgents 的「上下文影响」标为**完全隔离**，与 Skills/MCP/Hooks 形成对照：

| 维度 | SubAgents | 说明 |
|------|-----------|------|
| 扩展什么 | Claude 的**容量** | 突破单上下文能装下的工作量 |
| 运行位置 | **独立 loop** | 自己的消息循环 |
| 决策者 | 独立 LLM | 自己的模型实例 |

> 对照 opencode：opencode 的 subagent 是同类机制——主 agent 通过工具派发子 agent，子 agent 有独立上下文，返回结构化结果。两者思路一致，cc 的特殊之处在于把「编排」本身也交给了 prompt。

## 小结

- 多 agent 解决单 agent 的**上下文爆炸**和**任务混杂**——核心价值是「隔离子任务上下文，主 agent 只拿结论」。
- 协调者做**拆解、派发、验收、纠偏**，不自己搬砖。
- 协调者与 worker 通过**工具集隔离**：管理类（AgentTool/SendMessageTool/TaskStopTool）vs 执行类（Bash/FileEdit/...）。
- cc 的「**Prompt 即编排**」：编排算法写在 prompt 里，而非代码 DAG——大胆但有风险。
- 多 agent 是上下文工程 **Isolate** 策略的落地。
