## 动机：改了代码，怎么知道没改坏

harness 是基础设施。你改了核心循环、上下文压缩、会话存储——**怎么知道没把性能改坏？**

一个会话列表加载从 200ms 变成 2s，单个用户可能只感觉「有点卡」，但放大到百万用户就是灾难。评测（benchmark）和可观测（trace/telemetry）回答的就是：**给 harness 建立一套「体检」机制，性能回退能被量化地发现，而不是靠用户投诉。**

注意区分：这一章测的是 **harness 本身**（循环、会话、IO 快不快、稳不稳），不是「模型聪不聪明」——那是另一个领域。

## 直觉层：给 harness 做「体检」

想象 harness 是台发动机，评测就是定期体检：

- **测什么**：不是测「车跑得快不快」（那是模型的事），而是测「发动机转得顺不顺、耗不耗油」（循环、会话、内存）。
- **怎么测**：固定工况、固定赛道，跑一遍计时。工况不固定，成绩就没法对比。
- **体检报告**：每个指标有个「及格线」（预算），超了就是异常，要查原因。

体检的难点在「工况固定」——真实用户数据每天都在变，用真实数据测不出「这次和上次比」。所以要用**合成输入**（固定生成的数据）。

## 根源理解：三大原则的由来

从「harness 是基础设施」这个前提，推出三个原则：

1. **按用户路径组织**：基础设施的性能问题，用户感知在「打开会话列表卡不卡」这种操作上。测内部函数没用，要测用户真正走的路。
2. **合成输入可复现**：真实数据每天变，测不出「这次和上次比」。用固定常量生成输入，每次跑都一样，才能稳定对比。
3. **预算断言防回退**：性能回退不能靠「感觉慢了」，要靠「超了预算就失败」——把性能门槛写死，回退立刻暴露。

## 从零实现：计时 + 预算断言

`d2a-harness/src/step-06-eval/bench.ts`：

```ts
async function benchmark(fn, samples = 5, budget = 200) {
  const timings = [];
  for (let i = 0; i < samples; i++) {
    const start = performance.now();
    await fn();                              // 跑被测的「用户路径」
    timings.push(performance.now() - start);
  }
  timings.sort((a, b) => a - b);
  const median = timings[Math.floor(timings.length / 2)];  // 中位数更稳
  return { median, pass: median < budget };  // 预算断言
}
```

三个要点：**测用户路径**（不是内部函数）、**多次采样取中位数**（单次抖动大）、**预算断言**（超了就失败）。

## 对照基准：deepseek-harness 的 benchmark 体系

deepseek-harness 的 `benchmarks/AGENTS.md` 是一份成熟的评测方法论，正好印证这三个原则：

**按用户路径组织**（而非按包结构）：

```text
benchmarks/
├── session-corpus/      # 会话列表 / 搜索 / fork 的性能
├── conversation-fold/   # 对话折叠
├── terminal-io/         # 终端 IO
└── long-session-browser/# 长会话浏览器
```

每个目录对应一条**用户能感知的路径**（「打开会话列表卡不卡」），而不是内部模块。

**合成输入 + 固定预算**（两条硬规则）：

> "Synthesize fixed inputs from reviewed constants. Never use recorded Sessions, user material, or network services."（用固定常量合成输入，不用真实 session、用户材料、外部网络）

> "Pass every budgeted wall-clock endpoint to `recordTimings` before asserting it."（每个计时端点先记录，再断言预算）

**测量 wall-clock + 内存**：不止计时，还记录进程峰值 RSS（`recordPeakMemory`），甚至能在 cgroup 限制内存（4G/8G）下重跑测内存压力。

一句话总结：我们写的「计时 + 预算断言」，就是 deepseek-harness benchmark 体系的骨架。它多出来的，是**按用户路径的目录组织**、**合成输入的严格约束**、和**内存维度的测量**。

## 小结

- 评测测的是 **harness 本身**的性能/稳定性，不是模型智商。
- 三大原则：**按用户路径组织、合成输入可复现、预算断言防回退**。
- 测量要**计时 + 内存**双维度，中位数比单次采样稳。
- 评测（离线防回退）与可观测（在线 trace 定位）是同一件事的两面。

## 练习（动手）

1. 给 `benchmark` 加「内存测量」：用 `process.memoryUsage().rss` 记录峰值内存。
2. 实现「回归告警」：连续 N 次超预算就报错退出（对应 cc 的熔断器思想）。
3. 用固定合成输入（如 1000 条会话）测「会话列表」这个用户路径，而不是测内部函数。
