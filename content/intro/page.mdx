## 动机：为什么需要 harness

你可能遇到过这种情况：你让大模型「帮我修一下这个 bug」，它认真地回了一段文字——告诉你去改哪个文件、怎么改、改完怎么测。但**它自己不会去改文件，不会跑测试，也不会看报错**。

大模型本质上是「会说话的」，不是「会干活的」。它只能生成文字，不能执行动作。

**harness 就是把大模型从「会说话」变成「会干活」的那层框架。**

这影响两类人：

- **个人开发**：你装个 Claude Code / opencode / Codex，它就能直接读你的代码、改文件、跑命令、看报错，而不是只给你文字建议。
- **云端 agent**：像 xiaoaiclaw、coro 这样的线上服务，要同时服务海量用户，harness 决定了它能不能稳定、安全、低成本地跑。

一句话：**大家用 LLM 效率不高，往往不是模型不够强，而是没用好 harness 这层。**

## 直觉层：什么是 harness

「harness」本义是**马具 / 缰绳**——套在马身上的那套装备。

一匹好马力量很大，但你直接骑上去，它不会听你的、还可能把你甩下来。你需要缰绳、马鞍、马镫，才能把它的力气变成**可控的、朝你要的方向的拉力**。

大模型就是那匹马：

| 马 | 大模型 |
|----|--------|
| 力量大 | 能力强大（会写代码、会推理） |
| 不会自己干活 | 只会生成文字，不会执行 |
| 需要缰绳驾驭 | 需要 harness 套起来驾驭 |

所以这本书讲的，就是**怎么给大模型套上缰绳**——消息循环、工具调用、上下文管理、沙箱、多 agent 编排……一层层加装，直到它能稳定地替你干活。

## 机制层：一个最小 harness 长什么样

抛开所有复杂概念，一个最小的 harness 核心只有十几行伪代码——一个循环：

```text
messages = [系统提示词, 你的请求]

while 还没结束:
    reply = 大模型(messages)          # ① 让模型生成下一步
    if reply 里要求调用工具:
        result = 执行工具(reply.工具)  # ② 真正执行动作
        messages.append(result)        # ③ 把结果喂回模型
    else:
        return reply                   # ④ 没有工具要调，结束
```

这四步就是所有 agent 的「心跳」：

1. **调用模型**——让模型决定下一步该说什么、该调什么工具
2. **执行工具**——真正去改文件、跑命令、查数据
3. **回填结果**——把执行结果放回对话，让模型「看到」发生了什么
4. **判断结束**——模型不再要求调工具，任务完成

真实 harness（opencode / Codex / Claude Code）都在这个循环之上，加装了工具系统、上下文管理、沙箱、多 agent 协作、评测可观测等能力——这正是本书后面七章要逐一拆开的东西。

## 源码层：真实 harness 的骨架

一个真实 harness 的骨架，通常长这样（以 opencode 这类开源项目为例）：

```text
src/
├── loop/        # 上面的消息循环：驱动 agent 反复「调用模型 → 执行 → 回填」
├── tools/       # 工具系统：定义、执行、结果回传
├── context/     # 上下文管理：塞什么进模型、什么时候压缩
├── session/     # 会话状态：一轮对话的完整生命周期
└── transport/   # 与模型 API 通信
```

对比那十几行伪代码，你会发现：**核心循环没变，但每一环都变成了一个子系统**。本书的结构，就是按这个骨架展开——从「核心循环」出发，逐步加装「工具调用」「上下文与记忆」「沙箱与安全」「多 agent 编排」，最后到「评测与可观测」和「前沿与生产」。

## 小结

- harness 是**把大模型变成 agent 的框架**，核心是一个「调用模型 → 执行工具 → 回填结果」的消息循环。
- 大模型只会生成文字，**不会执行**；harness 让它能改文件、跑命令、查数据。
- 个人开发和云端 agent 的效率，都取决于 harness 这层做得好不好。
- 本书严格基于**真实主流 harness 源码**（opencode / Codex / Claude Code 等）讲解，由浅入深。
